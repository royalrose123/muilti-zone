    1. 摘要

    網站由多個各自建置、各自部署的 Next.js 應用（zone）組成，使用者只看到單一網域。入口 zone A 依路徑前綴把請求轉給負責的 zone。同一個 zone 內切頁是 client-side navigation，跨 zone 一律整頁載入。

    demo 用三個刻意不同的 zone 驗證：A 是 Next 15 App Router，B 是 Next 16 App Router，C 是 Next 15 Pages Router + React 18。三者可以共存，但必須遵守幾條規則（§6），其中最重要的一條是：不同 zone 要當成彼此不相容的應用看待，任何進入另一個 zone 的導頁都必須是整頁載入。

    四個關鍵決策：

    1. 分流：demo 由 A 的 rewrites 分流。正式環境是否改由 Ingress 分流，列為待審議（§3.1、§9）。
    2. 部署：每個 zone 獨立部署，改哪個 zone 就只部署哪個（§4.2）。
    3. 選單：放在 ConfigMap，由 A 擁有，B、C 在執行期向 A 取得並快取，另有兩層備援。改選單只需要重新部署 A，B、C 約 60 秒內跟上（實測 56～57 秒）（§5）。
    4. 同一頁混用其他 zone 的元件：用 Web Component。C 的現有元件不用改寫，C 單獨部署 A 就拿到新版（§7）。

    主要代價：A 是單點；B、C 為了顯示選單改成每次請求 render；跨 zone 的切頁體驗是整頁載入。

    2. 為什麼選 Multi-Zones

    表 1　前端拆分方式比較
    方式獨立部署各自選 Next／React 版本使用者體驗主要成本
    單一 Next app（monorepo 內分資料夾）否，任何改動都部署整站否全站 soft navbuild 時間、發版互相阻擋、升級要全站一起
    Multi-Zones 採用是是（已驗證 15／16、App／Pages、React 18／19 混用）zone 內 soft nav，跨 zone 整頁載入跨 zone 規則（§6）、共用 UI 要另外維護一致
    Module Federation（執行期載入別的團隊的元件）是實務上要對齊，React 必須共用同一份全站 soft navNext 官方未支援 App Router；版本耦合，出錯時難以追查
    iframe 或伺服器端拼接 HTML是是差：高度、路由、SEO、樣式都要另外處理整合成本高

    Module Federation 是什麼？網頁在使用者打開時，才從其他團隊的伺服器下載一段程式（例如購物車區塊），直接放進同一個畫面裡。好處是不同團隊做的東西可以出現在同一頁，切換畫面時也不必整頁重新載入。

    代價是這些程式在瀏覽器裡要共用同一套底層程式庫（例如 React），各團隊的版本必須保持一致。一個團隊升級，就可能弄壞別的團隊的畫面，而且這類問題要等使用者打開頁面才會出現，比較難事先發現。Next.js 官方目前也不支援在 App Router 上這樣使用。

    打個比方：Multi-Zones 像同一條街上的不同店面，各自裝潢、各自營業，換一家要走出門再進門（整頁載入）。Module Federation 像同一間百貨公司裡的不同專櫃，逛起來沒有隔閡，但水電管線（底層程式庫）大家共用，一處施工就可能影響其他專櫃。

    適合 Multi-Zones 的條件：網站可以依網址前綴切成幾個區域，每個區域由不同團隊負責或有不同的發版節奏，而且同一個頁面不需要混用不同團隊的元件。跨區域的切換頻率不高，使用者可以接受這時整頁載入。

    不適合的情況：同一頁要拼不同團隊的區塊，或是使用者會頻繁在區域之間來回切換。

    3.1 分流放在哪裡

    表 3　分流位置比較
    做法優點缺點
    A 的 next.config rewrites demo 採用官方建議的做法；規則和程式碼放在一起，本機開發與部署行為一致所有流量多經過 A 一跳；A 停止時全站停止；zone 位址在 A build 時就寫死
    A 的 middleware／proxy可以在執行期決定轉到哪裡每個請求都要多跑一段程式，延遲較高；Next 15 叫 middleware、Next 16 改名 proxy，寫法不同
    外部 gateway（K8s Ingress／Nginx）B、C 不依賴 A 存活；少一跳；換 zone 位址不必重新 build A路由規則離開程式碼庫；§6.3 的兩條特殊規則要搬過去，而且需要條件比對能力；本機開發要另外模擬

    3.2 zone 用 assetPrefix，不用 basePath

    依官方文件，zone 只設 assetPrefix（例如 /shop-static），讓 B 的 JS、CSS 網址和 A 不衝突；頁面路徑直接寫在 app 的路由裡（app/shop/…）。Next 15 起不需要再額外寫 /_next 的轉換規則。basePath 會讓 zone 所有連結自動加前綴，A 轉發時還要處理前綴，比較複雜，demo 沒有採用。

    3.3 設定範例

    Multi-Zones 需要三件事同時成立：入口依路徑分流、每個 zone 的資源路徑分開、跨 zone 的連結整頁載入。以下以 shop zone 為例，blog 的寫法相同。

    ① 子 zone（B）：只多一行 assetPrefix，讓 B 的 JS、CSS 網址變成 /shop-static/_next/…，不會和 A 的 /_next/… 衝突。

    // b/next.config.ts
const nextConfig = {
  assetPrefix: '/shop-static',
};
export default nextConfig;

    ② 入口 zone（A）：用 rewrites 把路徑轉給 B。B 的位址在 build 時傳入（§6.5）。

    // a/next.config.ts
const SHOP_ZONE_URL = process.env.SHOP_ZONE_URL; // 例如 http://shop.internal:3000

const nextConfig = {
  async rewrites() {
    return {
      beforeFiles: [
        // 官方文件沒寫：B 的圖片最佳化請求不會帶前綴，依圖片路徑轉給 B（§6.3）
        {
          source: '/_next/image',
          has: [{ type: 'query', key: 'url', value: '/shop-static/.*' }],
          destination: `${SHOP_ZONE_URL}/_next/image`,
        },
      ],
      afterFiles: [
        { source: '/shop', destination: `${SHOP_ZONE_URL}/shop` },                          // 頁面
        { source: '/shop/:path+', destination: `${SHOP_ZONE_URL}/shop/:path+` },
        { source: '/shop-static/:path+', destination: `${SHOP_ZONE_URL}/shop-static/:path+` }, // JS、CSS、public 檔案
      ],
    };
  },
};
export default nextConfig;

    ③ 連結：同 zone 用 <Link>，跨 zone 用 <a>。由共用元件依路徑前綴判斷，不靠人記（§6.1）。

    // 共用的導覽元件（每個 zone 都用同一份）
const ZONE_PREFIXES = { shop: ['/shop'], blog: ['/blog'] }; // 必須和 A 的 rewrites 一致

function zoneOf(href) {
  for (const [zone, prefixes] of Object.entries(ZONE_PREFIXES)) {
    if (prefixes.some((p) => href === p || href.startsWith(`${p}/`))) return zone;
  }
  return 'main';
}

function ZoneLink({ href, children }) {
  return zoneOf(href) === CURRENT_ZONE
    ? <Link href={href}>{children}</Link>  // 同 zone：不重新載入頁面
    : <a href={href}>{children}</a>;       // 跨 zone：整頁載入
}

    如果入口改用 Ingress 分流，②的規則就搬到 Ingress，①和③不變。

    4. 部署

    4.1 部署單位

    每個 zone 是一個獨立的 image（output: 'standalone' 的多階段 Dockerfile），各自 build、各自部署、各自回滾。只有入口 zone 對外，其他 zone 只在內網。B、C 啟動時不依賴 A：A 不通時仍能靠備援選單啟動並提供服務。

    4.2 改了什麼要重新部署誰

    表 4　變更與部署範圍
    變更要重新部署說明
    某個 zone 的頁面或程式只有該 zoneMulti-Zones 的主要好處
    選單內容（ConfigMap）只有 AB、C 不用動，60 秒內跟上（§5）。用 Kustomize 的 configMapGenerator 時，改內容會自動觸發 A 重新部署
    zone 的內部位址A（重新 build）rewrites 的目的地在 build 時寫進 routes-manifest.json，執行期改環境變數無效（已實測）。A 的 image 因此綁定環境，staging 與 production 要各自 build
    新增一個 zone 或改路徑前綴A、新 zoneA 要加 rewrites，也要更新共用的前綴表，否則 A 會用 <Link> 連到新 zone（§6.1）。其他既有 zone 不必更新：它們把不認得的前綴當成 A 的路徑，本來就用整頁載入。新前綴屬於 Pages Router 的 zone 時，A 還要加對應的 _next/data 規則（§7.4）
    嵌在 A 頁面裡的 C 元件（Web Component）只有 CA 頁面重新整理就拿到新版（已實測：A 容器沒有重啟）（§7）
    共用導覽列的樣式或行為所有 zone沒有一起部署的那段時間，各 zone 會顯示不同版本（§6.6）
    某個 zone 升級 Next 主版號只有該 zone部署本身不受影響，但要重跑跨 zone 的導頁測試（§6.4）

    4.3 設定在 build 時還是執行期生效

    原則：能在執行期讀的，都不要寫進 build，這樣同一個 image 才能用在多個環境。唯一寫進 build 的是 zone 位址，原因是 rewrites 的機制如此。選單在執行期讀；build 時不需要選單，也不需要其他 zone 在跑（已實測：A 停止時，B、C 照樣 build 成功）。

    設定誰讀生效時機
    zone 位址（SHOP_ZONE_URL、BLOG_ZONE_URL）Abuild
    選單檔案（ConfigMap 掛成檔案）A；B、C 只在備援時讀啟動時
    A 的內部位址（MAIN_ZONE_URL）B、C執行期

    4.4 可用性：A 是單點

    A 同時是入口和選單來源。A 停止時：

    • 用 A 分流時：全站無法使用，B、C 的備援沒有機會發揮。A 必須多副本並設健康檢查。
    • 改用 Ingress 分流時：B、C 照常服務，選單用備援；只有 A 的頁面停止。

    也就是說，§5 的選單備援要在 Ingress 分流下才有完整價值。這是建議正式環境評估 Ingress 的主要原因。

    5. 選單管理

    5.1 需求

    1. 選單只有一個來源；改了之後重新部署才生效（現行規則）。
    2. 改選單只部署一個專案，不能變成三個專案都要部署。
    3. B、C 向 A 取得失敗時，仍要顯示一份真的選單。
    4. build 不依賴 A，也不需要選單。

    5.2 方案比較

    表 5　選單來源方案
    方案改選單要部署A 不通時結論
    每個 zone 程式碼裡各寫一份全部不受影響不採用：一定會越改越不一致
    每個 zone 啟動時各自讀同一份設定全部不受影響不採用：違反需求 2
    共用 npm 套件全部（還要先發套件）不受影響不採用：適合放元件，不適合放內容
    build 時寫進各 zone全部（還要重新 build）不受影響不採用：改選單要全部重新 build
    瀏覽器端向 A 抓只有 A沒有選單不採用：選單不在初始 HTML，會閃動、不利 SEO
    A 擁有，B、C 在 server 端向 A 取得 + 快取 + 備援只有 A用快取或自己掛載的檔案採用

    另外評估過把選單 JSON 放進環境變數，不採用：.env、shell、compose 的跳脫規則各不相同，Next 讀 .env 還會展開 $，也沒辦法做結構化驗證。改成放檔案，環境變數只放檔案路徑。

    5.3 選單檔放在哪裡

    A 讀的是一個檔案，這個檔案從哪裡來是另一個決定。選單不是機密，不該放在 Vault 這類 secret 管理工具（第一版 demo 放在 Vault，已改掉）。

    表 6　選單檔的存放位置
    位置改選單的流程適合結論
    K8s ConfigMap，以檔案掛載改 deploy repo 的 menu.json → PR review → apply → A 重新部署工程團隊維護、不常改、需要 review 與版本紀錄採用
    Vault／K8s Secret改 Vault → 同步 → A 重新部署機密資料不採用：選單不是機密，改選單還要有 Vault 權限
    放進 A 的程式碼改程式碼 → 重新 build A → 部署幾乎不會變的內容不採用：違反「改設定只重新部署、不重新 build」
    後端 API 或 CMS在後台改，A 定期取得營運、PM 要自己改，而且不想走部署目前不需要；需求出現時，只要換掉「A 取得選單」這一段，B、C 不受影響

    用 Kustomize 時，可以讓 ConfigMap 內容一改就自動觸發 A 重新部署：

    # kustomization.yaml（A 的 deploy repo）
configMapGenerator:
  - name: site-menu
    files:
      - menu.json        # 內容改變 → ConfigMap 名稱帶的 hash 改變 → A 自動 rollout

# deployment.yaml（A；B、C 也掛同一份，當備援）
volumes:
  - name: menu
    configMap: { name: site-menu }
containers:
  - env: [{ name: MENU_FILE, value: /etc/config/menu.json }]
    volumeMounts: [{ name: menu, mountPath: /etc/config, readOnly: true }]   # 不要用 subPath

    ConfigMap 更新後，已掛載的檔案大約一分鐘內會自動換成新內容（用 subPath 掛載的除外）。A 只在啟動時讀一次，所以 A 仍然要重新部署才會生效；B、C 的備援檔則會自動變新。

    5.6 代價

    • build 時沒有選單，所以用到選單的頁面全部改成每次請求在 server render，失去整頁 CDN 快取。
    • 每個 Pod 各有一份快取。A 更新後最多 60 秒內，同一位使用者可能在不同 Pod 看到新舊不同的選單。

    6. Multi-Zones 會遇到的問題

    以下都是在 demo 中實際遇到或實測確認的問題。大多數問題的共同特徵是畫面看起來正常：Next 會退回整頁載入，使用者最後還是到得了，錯誤只留在 network 面板或 server log 裡，很容易漏掉。

    6.1 跨 zone 的連結必須整頁載入

    症狀
    在 A 用 <Link href="/shop"> 連到 B。dev 環境下 B 連續回 307，約 20 次後瀏覽器報 ERR_TOO_MANY_REDIRECTS，然後才改成整頁載入。production 環境下，只要打開含這個連結的頁面，prefetch 就會用 A 的路徑去載入 B 的 JS，產生 404 和 ChunkLoadError。
    原因
    <Link> 會用 A 自己的 client router 去要 B 的頁面資料，但兩邊是不同的應用，build、版本都不同。
    做法
    跨 zone 一律用 <a>。不靠人記：共用的導覽元件依網址前綴自動判斷該用 <Link> 還是 <a>，前綴表和 A 的 rewrites 是同一份。頁面內文的連結則要靠 code review 把關。

    6.2 靜態資源與 public 檔案衝突

    症狀
    每個 zone 的 JS、CSS 預設都在 /_next/static/，經由同一個網域時會互相覆蓋。
    原因
    所有 zone 共用同一個網域和相同的預設路徑；assetPrefix 也不會套用到 public/ 底下的檔案。
    做法
    每個 zone 設自己的 assetPrefix，public/ 的檔案一律放在 public/<prefix>/ 底下，網址就會落在既有的轉發規則內。

    6.3 官方文件沒寫的兩條路徑

    症狀
    ① Pages Router 的 zone 內 <Link> 沒有報錯，但默默變成整頁載入（只有 Pages Router 的 zone 會遇到）。② B、C 的圖片其實是由 A 的圖片最佳化器處理的，B、C 自己的 images 設定都沒有生效。
    原因
    _next/data（Pages Router 的頁面資料）和 _next/image（圖片最佳化）都不會加上 assetPrefix，請求會打到 A。這點已從 Next 15.5 與 16.4 的原始碼確認。
    做法
    在 A 加兩條優先比對的 rewrite：/_next/data/*/blog… 轉給 C；/_next/image 依 url 參數的前綴分別轉給 B 或 C。另一個做法是讓 B、C 全部的圖片都關掉最佳化（unoptimized），這樣問題就不存在，但代價是失去圖片最佳化，所以不採用。改用 Ingress 分流時，這兩條規則要一起搬過去。

    6.4 zone 內切頁被 redirect 到別的 zone

    症狀
    在 B 的頁面點 zone 內的 <Link>，目的頁在 server 端 redirect() 到 A 的頁面（例如權限不足導去 A）。最後確實到了 A，但 A 先回了 500（The router state header was sent but could not be parsed），之後才改成整頁載入。
    原因
    App Router 的 server 端 redirect 會讓 client router 繼續用 RSC 請求去要目的頁。目的頁在 A，A（Next 15）看不懂 B（Next 16）送來的 router state 格式。Pages Router 收到 redirect 會直接整頁載入，沒有這個問題。
    做法
    不要讓 zone 內的 soft nav 被 redirect 到別的 zone：已知會被導走的連結改用 <a>，或依條件切換 <Link>／<a>。demo 改完後 A 的 error log 是 0 筆。一般原則：zone 可以各自升級版本，但每次升級都要重跑跨 zone 的導頁測試；就算版本相同，不同 zone 也是不同的 build，不要假設它們能互相處理 RSC 請求。

    6.5 zone 位址在 build 時寫死

    症狀
    在執行期把 A 的 SHOP_ZONE_URL 改成無效位址，/shop 仍然由原本的 B 回應。
    原因
    rewrites 在 build 時就已經算好，寫進 routes-manifest.json。
    做法
    A 的 image 依環境分別 build，zone 位址在 Dockerfile 裡用 build arg 傳入，沒傳就讓 build 失敗。或者改用 Ingress 分流（§3.1）。

    6.6 共用 UI 越改越不一致

    症狀
    導覽列、design token 在每個 zone 各有一份，時間一久就會出現差異。
    原因
    zone 各自部署，沒有機制保證它們用的是同一版。
    做法
    demo：三份逐字相同的檔案，加上一個比對腳本（同時檢查 Tailwind、TypeScript 的版本）。正式專案建議抽成共用套件，React 和 next/link 設為 peer dependency，各 zone 自己決定何時升級；並接受部署期間各 zone 版本不同的那段落差。

    6.7 CSS 會不會互相污染

    結論
    不會在執行期互相污染。跨 zone 一定是整頁載入，同一個頁面裡只會有一個 zone 的 CSS；各 zone 的 CSS 也因為 assetPrefix 而路徑不同。
    真正的風險
    各 zone 的 Tailwind 版本、token 或 reset 不一致，導致共用的導覽列在不同 zone 長得不一樣。做法和 §6.6 相同：token 放共用檔案，Tailwind 鎖同一個精確版本並自動比對。

    6.8 App Router 執行的 React 版本不是你宣告的那個

    觀察
    App Router 執行的是 Next 內建的 React canary，不是 package.json 宣告的版本；只有 Pages Router 才會用到你安裝的 React。所以 App Router 的 zone 宣告 React 18 時，執行期其實是 19，型別和測試卻用 18。
    做法
    App Router 的 zone 宣告的 React 版本和 Next 對齊（19）。React 18 只有 Pages Router 的 zone 才真的用得到。

    7. 在同一頁嵌入其他 zone 的元件

    Multi-Zones 以「整頁」為單位分工。實務上常會遇到「A 的頁面只有一個區塊屬於 C」，例如 A 的首頁要放 C 的訂單列表。demo 驗證了這個情境的做法。

    7.1 需求

    1. C 已經在自己頁面上使用的元件，不需要改寫就能放進 A 的頁面。
    2. 元件自己取資料，A 只傳必要的參數（例如訂單編號）。
    3. C 單獨部署後，A 不需要任何動作就拿到新版。
    4. C 的樣式不影響 A，A 的樣式也不影響 C。

    7.2 方案比較

    7.4 實作時要注意的事

    元件
    widget 不是在 Next 裡執行，元件不能 import next/*（Link、router、Image）。導頁這類行為改成用 props 從外面傳入。Server Component 要拆成「只吃 props 的畫面」與「取資料」兩層。Pages Router 的元件本來就是吃 props，通常可以直接用。
    樣式
    • global.css 在 Next 裡是 layout 匯入的，widget 不會自動帶入，入口要自己匯入一次。
    • 放進 Shadow DOM 後，:root、body 規則不生效，要補 :host；@font-face 要放在 A 的頁面上。
    • Tailwind 用到 @property 的 utility（陰影、漸層、transform）在 Shadow DOM 內不生效，需要把 @property 規則另外注入到頁面上。
    路由
    • Pages Router 的 API 只能放在 /api/*，而 /api 屬於 A。C 要在自己的設定把 /member/api/* 轉到 /api/member/*。
    • 給 Pages Router 的 zone 新增前綴時（例如 /member），A 除了頁面規則，還要加 /_next/data/*/member/* 的規則，否則 C 內的切頁會默默變成整頁載入（§6.3 的同一個問題，demo 實際踩到）。
    載入
    next/script 載入 module 時要加 crossOrigin="anonymous"，否則 Chrome 會警告 preload 沒被使用，檔案下載兩次。
    代價
    沒有 SSR，內容要等 JS 執行完才出現（A 要預留高度）；頁面上會有兩份 React（A 一份、widget 一份），widget 約 115 KB（gzip）；不適合需要 SEO 的區塊。

    9. 風險與待審議

    9.1 風險

    項目影響程度因應
    A 是入口，也是選單來源A 停止時全站無法使用高多副本 + 健康檢查；評估改用 Ingress 分流
    zone 之間的版本差異soft nav 碰到別的 zone 時出錯，畫面卻看不出來中跨 zone 導頁測試列入每次升級的必測項目；監控 A 的 5xx
    有選單的頁面每次請求都要 renderserver 負載增加中選單已經有快取，額外成本主要是 render 本身；需要用正式流量評估
    共用 UI 越改越不一致各 zone 的導覽列長得不一樣中共用套件 + CI 檢查版本
    嵌入的元件與 A 頁面不同步C 改了元件的屬性或事件格式，A 沒跟上就會壞掉中把標籤名稱、屬性、事件當成對外合約，只增不改；改動時保留舊版一段時間
    A 的 image 綁定環境每個環境要各自 build低流程上接受；改用 Ingress 後就不需要

    9.2 待審議事項

    1. 正式環境的分流：沿用 A 的 rewrites，還是改用 Ingress？改用 Ingress 可以解決 A 單點和「zone 位址寫在 build 裡」兩個問題，但 §6.3 的規則要搬到 Ingress，本機開發也要另外模擬。
    2. 共用導覽列的形式：抽成共用套件的話，發版和升級的責任歸誰？
    3. 選單生效時間：目前最慢 60 秒。業務上可以接受多久？
    4. 各 zone 的 Next 版本策略：允許各自升級（每次重跑跨 zone 測試），還是規定同一個主版號？
    5. 哪些元件要做成 Web Component：只限「要讓其他 zone 嵌入、而且不需要 SEO」的區塊？標籤與事件的合約由誰維護？
    6. 可觀測性：導覽列已經標示選單來源（正常、過期、備援檔、空），是否送進監控並設告警？A 的 5xx 是否要特別監控跨 zone 的 RSC 請求？

    驗證方式是用 curl 檢查狀態碼與回應來源，再用 headless Chrome 實際點擊並讀取頁面狀態。本機 dev、本機 production、Docker Compose 三種環境都跑過。

    zone 內切頁／跨 zone 切頁zone 內是 soft nav（document 沒有重新載入），跨 zone 是整頁載入，三個 zone 都相同
    靜態資源、_next/data、_next/image都由正確的 zone 回應
    執行期改 zone 位址沒有效果，證明位址在 build 時寫死
    選單檔改了但還沒重新部署三個 zone 仍是舊選單（符合現行規則）
    只重新部署 AA 立即更新；B、C 在 56～57 秒時更新，容器沒有重啟（Vault 版與 ConfigMap 版各測一次）
